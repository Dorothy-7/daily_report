- PRを作成

### 分かったこと
- mergeは履歴をそのまま残して合流させる。
- rebaseは枝分かれの起点をずらして履歴を一直線にする
- conflictはGitが「どっちを採用するか」を判断できないだけで、エラーではない。
   該当箇所を自分で直してadd→commitすれば解決
- rebaseはpush済みのブランチにはやらない（履歴が書き換わって他の人とズレる）
- チーム開発の基本の流れ：mainからブランチを切る → 作業 → push → PR → レビュー → merge → ローカルでmainをpull
- git remote add origin でローカルとリモートが紐づく。
- 最初のpushは -u を付けておくと以降は git push だけで済む
- PRは「mergeしてください」の依頼であると同時に、レビューしてもらう場でもある

### 感じたこと
- mergeとrebaseはどちらも「ブランチを合流させる」なのに、履歴の見え方が全然違うのが面白い。
- どっちを使うかはチームのルール次第っぽい
- conflictは最初こわかったが、仕組みが分かれば「Gitが聞いてきてるだけ」なので落ち着いて対応できそう
- PRの流れを一通り触って、ようやくチーム開発の入口に立てた感じがする。演習で手を動かして定着させたい

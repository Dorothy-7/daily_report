## 分かったこと

### 通知テーブル（今日一番大事だったところ）
- 通知は「誰に届くか」「誰がやったか」「何をされたか」「どのツイートか」を1行にまとめる
- 受け取る人（receiver_id）と、やった人（actor_id）は、どっちも users の番号。follows や DM と同じで users を2回指す
- いいねとフォローの2種類があるので、action という列に like か follow を入れて区別する
- tweet_id だけは null にする。フォローの通知には対象のツイートがないから

| receiver_id | actor_id | action | tweet_id |
|---|---|---|---|
| 1 | 2 | like | 5 |
| 1 | 3 | follow | （空） |

- 最初は tweet_id を not null にしていた。そのままだと2行目が登録できず、フォローの通知が送れなくなる
- 「行ができた瞬間に値が入っているか」で決めるのは users と同じ。ただ今回は「通知の種類によって、入るときと入らないときがある」というパターンだった
- 線の記号も変わる。tweet_id が空のこともあるので、tweets 1--* ではなく tweets ?--* と書く（? は 0か1）
- 最初は followed_id という名前にしていたが、意味が逆だった。いいねの通知でも使う列なので、フォロー専用の名前ではなく actor_id にした

### 中間テーブル
- いいねは「人 × ツイート」の記録なので、user_id と tweet_id を持つ likes テーブルにする
- retweets と bookmarks は likes と同じ形。テーブル名を変えるだけ
- 外部キーの列名は単数形。tweets_id ではなく tweet_id
- 同じ人が同じツイートに2回いいねできないように、uniq(user_id, tweet_id) と2つの組み合わせで指定する
- uniq(user_id) と1つだけにすると「1人1回しかいいねできない」になってしまう

### フォローとDM
- どちらも users を2回指すので、同じ名前にできない。follower_id / followed_id、sender_id / receiver_id と役割で名前を分ける
- 線の本数は「users を指す列の数」と同じ。だから2本
- 線に {label: "follower_id"} と付けるのは名札。名札なしの線と同じものなので、両方書くと線が4本になってしまう
- DMの本文は文字数制限がないので text。140文字はツイートだけ

### PDFとPR
- twitter.er は文字で書いた設計、out.pdf はそれを図にしたもの。直すのは必ず .er のほう
- PDFはエディタでは開けない。警告が出るけど失敗ではなく、open コマンドでプレビューで開く
- ER図は「どのテーブルがどうつながるか」、テーブル定義は「文字数やインデックスまで決めたもの」
- PRの説明欄に「特に見てほしい点」を書いておくと、自信がないところを質問できる

### Git
- 保存してからコミットする。保存前にコミットすると、直した内容が入らない
- タブに白い丸が出ていたら未保存。git status で modified が赤字なら、保存済みだけどまだコミットしていない
- テーブルを1つ書くたびにコミットしたので、履歴を見れば作った順番が分かる

### POAよりDOA（DB設計徹底指南書 第1章）
- 処理（画面や機能）は業務が変わるとすぐ変わるが、データはあまり変わらない
- だから先にデータを決めて、処理はその後に考える。これがDOA
- 処理から先に作ると、機能ごとに同じデータがバラバラにできてしまう

### 3層スキーマ（第1章）
- 外部スキーマ：ユーザーやアプリから見える姿（画面、ビュー）
- 概念スキーマ：テーブル定義。論理設計で作るのはここ
- 内部スキーマ：実際にどう保存するか（ファイル、インデックスなど）
- 真ん中に概念スキーマがあるおかげで、保存方法を変えても画面側に影響が出にくい

### 論理設計と物理設計の流れ（第2章）
- 論理設計：エンティティの抽出 → エンティティの定義 → 正規化 → ER図
- 物理設計：テーブル定義 → インデックス定義 → ハードウェアのサイジング → ストレージの冗長構成 → ファイルの物理配置
- 論理設計は「何を持つか」、物理設計は「どこにどう置くか」
- 今日の課題でやった .er とER図は論理設計、テーブル定義は物理設計の入口にあたる

### レプリケーションとバックアップの違い（第2章）
- レプリケーション：今のデータを別のDBにほぼリアルタイムでコピーし続ける
  - 目的は「止めないこと」。本番が壊れてもすぐ切り替えられる
  - 弱点は、間違ったDELETEもそのままコピーされること。過去には戻れない
- バックアップ：ある時点のデータを別の場所に保存しておく
  - 目的は「過去に戻せること」。誤操作やデータ破損に効く
  - 弱点は、戻すのに時間がかかること。バックアップ後の更新は入っていない
- 守っているものが違うので、どちらか片方ではなく両方必要

| | レプリケーション | バックアップ |
|---|---|---|
| 守るもの | サービスが止まらないこと | データを過去に戻せること |
| 持っているデータ | 今の状態だけ | 過去のある時点 |
| 機械の故障 | 強い（すぐ切り替え） | 戻すのに時間がかかる |
| 誤って削除 | 防げない（一緒に消える） | 戻せる |

### リストア・ロールフォワード・リカバリの違い（第2章）
- リストア：バックアップファイルをDBに戻す。戻るのは「バックアップを取った時点」まで
- ロールフォワード：リストアした後、トランザクションログを順番に当てて、障害の直前まで進める
- リカバリ：リストアとロールフォワードを合わせた、復旧作業の全体

```
0:00 バックアップ取得        15:00 障害発生
  |--------------------------------|
  ① リストア      → 0:00 の状態に戻る
  ② ロールフォワード → 0:00〜15:00 の更新をログで再現する
  ①＋② ＝ リカバリ
```

- リストアだけだと、0:00〜15:00の更新が全部消える
- だからバックアップだけでなく、トランザクションログも残しておかないと直前まで戻せない

### クラウドの場合の冗長構成（第2章、AWSの例）
- オンプレでは自分でサーバーを並べて組むが、クラウドでは設定で選ぶだけになる
- マルチAZ：同じリージョンの別のデータセンターに予備のDBを置く。本番が落ちたら自動で切り替わる
- リードレプリカ：読み取り専用のコピー。参照の負荷を分散できる。少し遅れて反映される
- 別リージョンへのコピー：地域ごと被災したときの備え
- バックアップも自動で取られ、ログと合わせて「指定した時刻の状態」に戻せる
- 仕組みを自分で組まなくてよくなっただけで、中でやっていることはレプリケーションとバックアップ
